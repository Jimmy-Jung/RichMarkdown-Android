# richmarkdown-core 개선 제안

기준일: 2026-10-06 · 개선 승인 후 진행 상태

`CoalescingWorker`는 실행 중 1건과 최신 대기 1건만 유지하는 요청 관리자입니다. 대기 입력을 꺼내 실행하는 반복 작업을 drain이라고 하며, 여러 작업의 수명을 묶는 CoroutineScope(scope) 안에서 실행합니다. 아래에서는 이미 수정한 취소 문제와 실제 사용 근거가 없어 보류한 장기 수명 문제를 구분합니다.

## AC-I01: 요청 처리 중단 뒤 상태 정리 검사

**상태: 구현·회귀 추가.** 회귀 테스트는 수정 후 기존 동작이 다시 깨지지 않는지 확인하는 검사입니다. 변경 전 `cancellationBeforeDrainStartsReleasesIdle`의 기대값 검사(assertion)가 실패해 시작 전 취소에서 미처리 작업 상태(outstanding)가 남는 결함을 확인했습니다. drain 코루틴이 시작하지 않으면 기존 `finally`의 상태 정리에도 도달하지 않았습니다.

**적용:** ATOMIC은 시작 전에 취소됐더라도 코루틴 본문에 진입하게 하는 시작 방식입니다. 이를 사용해 상태 정리(cleanup)가 실행되게 하고, `try` 안의 첫 취소 검사로 실제 작업인 `perform`을 막습니다. 대기 입력을 버린 뒤 작업이 없는 상태(idle)가 되며 실행 위치를 정하는 dispatcher와 동시 실행 최대 1 계약을 유지합니다.

**회귀:** 시작 전 취소·취소된 scope에 재제출·실행 중 취소·작업 예외·살아 있는 scope에서의 재시작을 [CoalescingWorkerTest](../../../richmarkdown-core/src/test/)에 추가했습니다. 이 내용은 기존 개선 기록이며 이번 문서 작업에서 테스트를 새로 실행한 것은 아닙니다. 최종 실행 성공은 [검수 기록](../validation.md)에서 확인합니다.

## AC-I02: 요청번호의 최대값과 장기 사용 기준

**상태: 보류.** `generation`은 호출자가 붙이는 요청 순서번호이며 지금까지 받은 가장 큰 번호를 high-water라고 합니다. 일반 문서·스트리밍 세션이 2,147,483,647회 제출을 넘는 수명 요구나 측정은 없습니다. 이번 개선에서는 공개 generation 타입을 바꾸지 않습니다.

`Long`으로 바꾸더라도 숫자가 최종 최대값을 넘는 문제(overflow)는 사라지지 않습니다. 실제 장기 사용 근거가 생기면 화면 데이터 모델과 worker를 함께 검토합니다.

- **관찰:** worker의 최대 수신 번호와 상위 모델의 generation은 `Int`이며 최대값을 넘었을 때 안전하게 번호를 다시 시작하는 처리가 없습니다. worker는 이전 최대값 이하를 항상 거부합니다.
- **발생 조건과 영향:** 한 모델 인스턴스에서 요청번호가 최대값을 넘어 값이 되돌아가면(wrap) 새 요청이 과거 값으로 판정될 수 있습니다. 일반적인 문서 수명에서 이 횟수에 도달한다는 측정은 없으며 우선순위는 낮습니다.
- **최소 변경 제안:** 장기 자동 입력 등 실제 수명 요건이 생기면 모델과 worker를 함께 `Long`으로 변경하거나 안전한 요청번호 재시작 규칙을 정합니다. worker만 바꾸면 호출자에서 발생하는 정수 범위 초과를 해결하지 못합니다.
- **필요 테스트:** 최대값 경계의 연속 제출에서 최종 값이 반영되고 작업이 없는 상태로 돌아가는지 모델·worker 양쪽을 검사합니다.
