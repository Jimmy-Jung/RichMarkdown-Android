# richmarkdown-highlight 개선 제안

기준일: 2026-10-06 · 개선 승인 후 진행 상태

Prism은 원문을 키워드·문자열 같은 문법별 조각(토큰)으로 나누는 코드 분석 라이브러리이며, QuickJS는 이 JavaScript 분석을 실행하는 엔진입니다. 여기서 네이티브(native) 실행은 JVM 밖의 QuickJS 라이브러리에서 수행하는 작업을 뜻합니다. JavaScript 실행 환경(context)의 수명과 실제 화면에 색을 반영하는 시점은 다른 책임입니다.

## AH-I01: 실행 시간과 대기 호출 경계 확인

**상태: 측정 필요, 런타임 변경 보류.** 100,000 UTF-16 제한 안의 실제 장기 실행·대기열(queue) 지연이 아직 재현되지 않았습니다. UTF-16은 Kotlin 문자열 길이에 쓰는 16비트 단위이며 이모지 하나가 두 단위를 차지할 수 있으므로 글자 수와 다릅니다.

재현 근거 없이 새 JavaScript 실행 환경이나 시간 초과 처리를 감싼 추상화(timeout abstraction)를 추가하지 않습니다. 코루틴에서 시간 제한을 걸었다고 네이티브 토큰화를 중단할 수 있다는 계약도 추가하지 않습니다.

- **관찰:** [소스](../../../richmarkdown-highlight/src/main/)의 `PrismHighlighter.kt`는 100,000 UTF-16 단위를 제한하고, 실행 환경을 동시에 쓰지 못하게 하는 Mutex 잠금으로 코드 분석을 순서대로 수행합니다. JavaScript 분석의 시간 제한이나 대기 호출(pending)을 최신 요청 하나로 합치는 처리는 없습니다.
- **발생 조건과 영향:** 허용 길이 안에서 문자열 패턴을 찾는 정규식 처리가 오래 걸리는 입력이나 한 코드 블록의 잦은 갱신은 이후 호출을 지연시킬 수 있습니다. 실행 시간을 측정하거나 특정 입력의 장기 실행을 재현한 결과는 아닙니다.
- **최소 변경 제안:** 고정 문법(grammar)의 긴 주석·문자열·닫히지 않은 구문을 준비한 입력(fixture)으로 실행 시간·대기열을 먼저 확인합니다. 문제가 확인되면 호출자(caller)에서 실행 중 1건과 최신 대기 1건만 유지하는 요청 합치기(latest-wins)를 우선 검토하고, 엔진 중단 기능(native interrupt)은 실제 지원하는 범위에서만 도입합니다. suspend `withTimeout`만 둘러서 네이티브 JavaScript 실행이 반드시 중단된다고 보장하지 않습니다.
- **필요 테스트:** 의도적으로 처리 비용을 높인 입력(adversarial)이 길이 상한 이내일 때, 취소된 대기 호출이 있을 때, 긴 실행 중 다음 요청과 release가 올 때를 확인합니다. 색 없는 원문으로 대체하는 동작(plain fallback), 복구, 네이티브 실행 환경의 수명을 구분해 검사합니다.

## AH-I02: 코드 분석과 해제 요청의 동시 호출 검사

**상태: 회귀 추가, 제품 수명 API 유지.** 수정 후 기존 기능이 다시 깨지지 않는지 확인하는 회귀 테스트를 `PrismHighlighterTest`에 추가했습니다. 실제 QuickJS에서 동시 spans 8개와 release 8회가 경합하는 검사를 4회 반복하며 원문·범위 동일성과 직후 재초기화를 확인합니다.

이 반복 경합 검사(stress)는 모든 실행 순서를 고정하거나 실행 환경의 해제 완료 시점을 보장하지 않습니다. 결과 변조·닫힌 실행 환경 사용을 재현한 근거가 없어 별도 suspend 해제·새 잠금·실행 환경 교체는 추가하지 않았습니다. 이번 문서 작업에서 테스트를 새로 실행하지 않았으며 기존 최종 실행 상태는 [검수 기록](../validation.md)을 따릅니다.

- **관찰:** `release`는 잠금을 즉시 잡는 `tryLock`이 실패하면 `releaseRequested`를 설정하고 spans의 `finally`가 이 표시(flag)를 읽습니다. [기존 Android 테스트](../../../richmarkdown-highlight/src/androidTest/)는 작업이 없는 상태(idle)의 release 후 동일 결과와 동시 spans 8개를 확인했습니다. 추가한 검사는 분석과 해제를 함께 시작하지만 토큰화 내부의 특정 순간에 release를 호출하도록 강제하지는 않습니다.
- **발생 조건과 영향:** 토큰화 종료·해제 요청 표시·Mutex 잠금 해제 시점이 겹칠 때 해제 요청이 어느 호출까지 지연되는지 명확하게 보장하지 않습니다. 현재 소스는 해제 완료 시점의 정확도를 의도적으로 보장하지 않습니다.
- **최소 변경 제안:** release 호출 완료를 '즉시 해제 완료'와 혼동하지 않게 유지합니다. 실행 환경의 수명 관리에서 완료 시점 보장이 필요할 때만 Mutex 안에서 처리하는 suspend 해제를 추가 검토합니다.
- **필요 테스트:** 분석 진행 중 release, 대기 spans가 있는 release, 직후 새 spans의 번들 재초기화를 반복하고 앱 중단(crash)·닫힌 실행 환경 사용·원문 변조가 없는지 확인합니다. 추가한 반복 경합 검사와 정확한 내부 시점을 제어하는 검사는 별개입니다.
