# richmarkdown-mermaid 개선 적용과 남은 검수

기준일: 2026-10-06 · 상태: **구현 반영 · 실행 검수는 validation 참조**

사용자 요청에 따라 아래 개선을 소스와 회귀 테스트에 반영했습니다. 회귀 테스트는 고친 문제가 다시 생기는지 확인하는 검사입니다. 각 항목은 수정 전 증상, 현재 동작, 남은 확인 범위를 구분합니다. [현재 명세](../spec/richmarkdown-mermaid.md)·[아키텍처](../architecture/richmarkdown-mermaid.md)는 반영한 동작을 설명하며 기존 실행 증거는 [validation](../validation.md)에 연결합니다. 이번 문서 보완에서 테스트를 다시 실행한 것은 아닙니다.

아래에서 앱 측(native)은 Kotlin 코드, 웹 측은 앱 내 웹 화면인 `WebView`에서 실행되는 JavaScript 코드입니다. DOM은 웹 문서의 화면 구조이고, SVG는 확대해도 선명한 벡터 그림 형식입니다.

## AM-I01: 취소한 요청의 늦은 결과 차단

이전 구현은 Kotlin의 응답 대기 목록인 `pending`에서 요청 ID만 지웠습니다. 따라서 늦게 끝난 JavaScript가 웹 화면을 이전 그림으로 바꾸는 동작은 막지 못했습니다. 현재는 앱 측 응답을 연결하는 요청 ID와, 웹 화면에 반영할 결과를 구분하는 번호인 generation을 별도로 관리합니다.

새 요청은 이전 앱 측 대기를 끝냅니다. `cancelDiagram(id)`와 기다리던 작업이 끝나는 각 `await` 뒤의 번호 검사로 이전 SVG·크기를 반영하지 않습니다. 화면에 내보내기 전 검사하는 숨긴 임시 영역(staging)에서 측정하고, 브라우저의 화면 갱신 단위인 frame을 마지막으로 기다린 뒤 최신 결과만 표시합니다.

JavaScript의 `Promise`는 나중에 완료될 결과입니다. 페이지마다 이 작업들을 대기열(queue)에 연결해 `initialize`·`render`를 하나씩 순서대로 실행합니다. 진행 중 렌더링을 취소하거나 15초 렌더 응답 제한(timeout)을 넘기면 페이지를 dirty 상태로 표시합니다. 이는 다음 요청 전에 페이지를 다시 불러와야 한다는 뜻입니다. 다음 요청은 페이지를 새로 불러오므로 끝나지 않는 이전 `Promise` 대기열에서 벗어날 수 있습니다. 실행 중 JavaScript를 강제로 멈추는 기능은 아닙니다.

이전 요청의 `finally` 정리는 최신 요청의 페이지 상태를 바꾸지 않도록 요청 ID를 검사합니다. 페이지 로드 URL에도 별도의 구분 번호를 붙여 이전 페이지의 완료·실패 콜백이 새 로드를 끝내지 못하게 합니다. 로드와 렌더링에는 각각 15초 제한을 적용하며 요청 전체가 15초 안에 끝난다는 뜻은 아닙니다.

iOS 패키지의 `Sources/RichMarkdownMermaid/Web/regression-test.mjs` 공유 JavaScript 회귀 테스트는 양쪽 HTML에 완료 시점을 제어하는 엔진을 주입합니다. 최종 웹 화면이 최신 요청과 일치하는지, 동시에 실행하는 엔진 작업이 최대 1개인지 확인합니다. JavaScript만 실행하는 VM 검사를 실제 WebView의 글꼴·화면 갱신 검사에 대한 대체 증거로 보지는 않습니다.

## AM-I02: 상위 화면에서 정한 다크 모드 전달

기존 다이어그램 함수는 시스템 다크 모드를 사용하므로 상위 Markdown 화면이 별도로 정한 밝기 설정을 전달하기 어려웠습니다. 현재는 `isDark` 인자를 받는 호환 overload를 추가했습니다. overload는 같은 이름에 인자 구성이 다른 함수입니다. 상위 Compose·View가 정한 값을 Mermaid 연결 구현(adapter)에 넘기고, 같은 설정을 SVG와 실패 대체 표시에 적용합니다.

기존 사용자 정의 구현과 이전 함수를 직접 호출하는 방식은 유지합니다. Mermaid는 전달된 값에 따라 dark/default로 초기화합니다. 원문 안의 렌더 설정(directive)이나 class·style에 적힌 자체 색을 모두 덮어쓰는 정책은 아닙니다. [회귀 테스트](../../../richmarkdown-mermaid/src/androidTest/)에 adapter가 값을 전달하는 검사가 있습니다. 시스템의 밝은·어두운 모드와 상위 화면의 우선 설정(override)이 만드는 모든 Compose 표시 조합은 별도 실행 확인 대상입니다.

## AM-I03: WebView 생성 실패 처리와 영구 제거 시 정리

기존에는 렌더러를 만드는 단계의 예외를 실패 원문 표시로 처리하지 못했고, 뷰를 영구 제거할 때 모든 작업을 정리하는 API도 없었습니다. 현재는 생성 예외를 `MermaidDiagramView`에서 잡아 오류 안내와 원문을 보여줍니다. 테스트 전용 생성 함수(factory)를 바꾸어 실패를 주입할 수 있습니다.

뷰가 잠시 창에서 떨어지는 단계(detach)는 다시 붙일 수 있도록 재사용합니다. 영구 제거할 때는 `dispose()`로 크기 콜백, 뷰에 속한 코루틴 작업 범위(scope), `pending` 대기, `WebView`, 자식 뷰를 정리합니다. Compose는 `onRelease`에서 이를 호출합니다. 기본 `RichMarkdownView`도 영구 교체된 뷰를 이전 공급자의 `disposeView` 정리 함수로 해제합니다. Mermaid가 만든 뷰만 정리하며 다른 종류의 컨테이너 뷰에는 작업하지 않습니다.

직접 뷰를 생성한 앱은 영구 제거할 때 `dispose()`를 호출해야 합니다. 생성 실패와 중복 `dispose()`를 검사하는 회귀를 추가했습니다. 여러 번 호출해도 이미 정리한 상태가 유지되는 동작을 멱등성(idempotent)이라고 부릅니다.

WebView 실행 구성 요소(provider)를 실제로 사용할 수 없는 환경과 장시간 부착·제거를 반복하며 메모리를 측정하는 검사는 별도입니다. 생성 실패 주입이나 `dispose()` 결과의 자동 판정(assertion)만으로 메모리 누수가 없다고 하거나 메모리 개선 수치를 주장하지 않습니다.

## AM-I04: 오류 시 원문 표시 상한

너무 큰 `source`를 거절한 뒤에도 실패 텍스트 뷰가 원문 전체를 표시하고 측정하던 문제를 고쳤습니다. 실패 표시만 UTF-8 20,000바이트 이내의 앞부분(prefix)과 생략 표식으로 제한합니다. Unicode의 각 문자 값을 구분하는 code point 경계에서 잘라, 한 문자 값을 UTF-16 두 단위로 저장하는 surrogate pair를 중간에 나누지 않습니다.

같은 그림을 다시 그릴지 비교하는 렌더 키는 `source` 문자열 전체를 필드로 보관하고 내용으로 비교합니다. 키를 만들기 위해 긴 원문을 별도 문자열로 다시 조합하지는 않습니다.

`source` 전체와 상위 코드 블록의 원문 복사는 보존합니다. 따라서 원문 전체의 메모리 보관 상한까지 해결한 것은 아닙니다. 여러 문자 값이 하나로 보이는 복합 이모지 전체(grapheme) 경계는 보장하지 않습니다. 조합된 이모지가 중간에서 나뉘는 문제와 직접 API의 원문 보관 상한은 정책을 정한 뒤 보완할 수 있는 남은 제한입니다. 과대 원문 회귀 테스트는 표시 상한과 생략 표식을 확인합니다.

## 후속 검수에서 보완한 종료 처리와 화면 표시

기존에는 렌더링을 마쳐 작업이 없는 상태(idle)에서 웹 실행 프로세스가 종료되면 뷰가 복구되지 않을 수 있었습니다. 현재는 종료 알림도 뷰 콜백으로 전달합니다. 연속 종료에는 한 번만 `WebView`를 교체해 재시도하고, 성공하거나 새 `source`·`theme`가 들어오면 재시도 횟수를 다시 사용할 수 있습니다. 재시도 횟수를 다 써도 종료된 `WebView`는 제거·폐기하며 새 입력에서 다시 만들 수 있습니다.

원문을 교체하면 이전 그림과 접근성 내용을 즉시 가리고 로딩 상태로 바꿉니다. 기존 SVG를 곧바로 삭제하는 방식은 아닙니다. 투명도와 접근성 표시를 바꾸어 가리고, 최신 결과가 확정되면 웹 화면의 SVG를 교체합니다. 코루틴 범위를 취소한 뒤 도착한 일반 오류도 이전 화면에 반영하지 않습니다.

추가 회귀는 독립적인 종료 두 번의 복구, 끝나지 않는 JavaScript 요청 교체 시 즉시 이전 그림을 가리는 동작과 다음 정상 요청의 복구, 임시 영역의 화면 갱신 대기 중 취소를 확인합니다. 테스트에서 종료 이벤트를 직접 전달하는 검사는 실제 OS가 프로세스를 강제 종료하는 상황의 재현과 다릅니다.

## AM-I05. 임시 HTML 라벨의 이벤트 실행 차단과 CSP 강화

같은 번들·HTML의 실행 검수에서 실제 결함을 확인했습니다. 원문 속 directive가 HTML 라벨을 켜면 strict 보안 모드에서도 임시 라벨의 `onerror` 이벤트가 실행됐습니다. SVG의 위험한 태그·속성을 제거하는 sanitizer가 처리하기 전 발생한 문제입니다. 이벤트 실행 여부는 테스트용 `window` 변수(flag)가 바뀌는지 확인했으며 실제 사용자 문서나 비밀정보는 사용하지 않았습니다.

최상위(root)·flowchart의 `htmlLabels`를 모두 끄고 기본 `secure` 목록에 `htmlLabels`·`dompurifyConfig`를 추가했습니다. `secure`는 원문으로 바꾸지 못하게 잠그는 설정 키 목록입니다. `dompurifyConfig`는 sanitizer인 DOMPurify의 설정입니다. 중첩 설정에도 잠금을 적용합니다.

CSP(Content Security Policy)는 허용할 스크립트와 자원 출처를 제한하는 규칙입니다. 스크립트 CSP의 `unsafe-inline`을 제거하고 로컬 번들과 정확히 일치하는 초기 실행 코드(bootstrap)만 허용합니다. 코드 일치는 SHA-256 해시로 확인합니다. 따라서 `onerror`처럼 HTML 속성에 적힌 이벤트 코드(inline event)도 별도로 차단합니다. 숨긴 임시 영역은 보안 격리 공간이 아닙니다.

Android 기기나 에뮬레이터에서 실제 WebView를 사용하는 계측(instrumented) 회귀는 directive와 원문 앞부분의 설정 문법인 frontmatter를 각각 확인합니다. SVG가 만들어지는지와 별도로 테스트 변수, strict, 최상위·중첩 HTML 라벨, sanitizer 설정 변경 여부를 검사합니다. sanitizer와 독립적으로 CSP가 `onerror`를 차단하는 실행 검사(probe)도 있습니다. 공유 JavaScript 회귀는 초기 실행 코드와 해시가 어긋나는지, 초기화 잠금과 `unsafe-inline` 금지가 유지되는지 확인합니다.

Mermaid 본체 11.17.2는 유지하고 DOMPurify 3.4.16·JavaScript KaTeX 0.18.2를 고정해 보안 개선 번들을 다시 생성했습니다. 기존 실행 증거는 validation에 기록하며, 이번 문서 작업에서 검사를 새로 실행한 결과로 표현하지 않습니다. 전체 공격 사례 모음(corpus)의 보안 인증으로 확대하지 않습니다.
