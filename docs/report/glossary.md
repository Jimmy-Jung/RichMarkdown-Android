# 보고서 용어 안내

작성일: 2026-10-07

이 보고서에서 반복해서 쓰는 용어를 Android의 실제 처리 흐름에 맞춰 설명합니다. API 이름과 설정 키는 소스에서 검색할 수 있도록 그대로 적고, 뜻은 한국어로 풀어 씁니다. 각 모듈 문서에도 처음 등장하는 용어의 설명을 덧붙였습니다.

## 문서와 모듈 구조

| 용어 | 이 보고서에서 뜻하는 것 |
| --- | --- |
| 아키텍처(architecture) | 어느 모듈이 어떤 일을 맡고, 입력과 결과가 어디로 전달되는지 정리한 구조입니다. |
| 명세(spec)·동작 계약 | 앱이 라이브러리를 사용할 때 지켜야 할 입력 조건, 반환값, 실패 처리 규칙입니다. 법률상 계약을 뜻하지 않습니다. |
| ADR(Architecture Decision Record) | 구조를 선택한 이유, 다른 방법의 비용, 다시 검토할 조건을 기록한 문서입니다. 기존 코드를 읽고 작성한 기록은 과거 회의나 팀 승인을 증명하지 않습니다. |
| Gradle 모듈(module) | 함께 빌드하는 소스와 의존성의 묶음입니다. 이 저장소의 배포 대상 라이브러리 모듈은 네 개입니다. |
| 패키지(package) | Kotlin·Java 소스에서 관련 타입을 묶는 이름 공간입니다. 이 보고서의 ‘패키지 보고서’는 배포할 라이브러리 전체를 가리키므로 문맥을 구분합니다. |
| JVM(Java Virtual Machine) | Java·Kotlin 코드를 실행하는 환경입니다. `richmarkdown-core`는 Android 화면 API에 의존하지 않는 JVM 모듈입니다. |
| 배포 파일(artifact) | 사용하는 앱에 전달하는 빌드 결과입니다. JVM 라이브러리의 JAR, Android 라이브러리의 AAR, 의존성 정보를 담은 POM·Gradle metadata 등이 해당합니다. 파일 생성과 원격 저장소 발행은 별도 단계입니다. |
| `api`·`implementation` 의존성 | `api`는 사용하는 앱에도 의존 모듈의 API를 노출하고, `implementation`은 구현에 필요한 의존성을 모듈 안에서 다루는 Gradle 설정입니다. |
| 선택 기능(opt-in) | 앱이 명시적으로 켜거나 추가해야 사용하는 기능입니다. 내부 API의 opt-in 표시는 해당 API 사용에 동의해야 한다는 별도 의미도 있습니다. |
| 공급자·구현체(provider) | 약속된 인터페이스에 따라 실제 일을 수행하는 객체입니다. 코드 색칠 공급자는 코드와 언어를 받아 색을 입힐 구간을 반환합니다. |
| desugaring | 일부 Java API를 이전 Android 버전에서도 쓰도록 빌드 때 보완하는 기능입니다. 예제 앱의 설정을 라이브러리 전체의 최소 OS 보장으로 확대하지 않습니다. |

## 원문을 분석하고 위치를 보존하는 과정

**파싱(parsing)**은 Markdown 문자열을 제목·문단·목록 같은 구조로 읽는 과정입니다. **렌더링(rendering)**은 그 구조를 화면의 글자·표·그림으로 표시하는 과정입니다. 같은 문서를 분석하더라도 화면 색이나 글자 크기는 별도로 바뀔 수 있습니다.

| 용어 | 뜻과 사용 예 |
| --- | --- |
| 원문(source) | 앱이 전달한 Markdown, 코드, 수식 문자열입니다. 분석하거나 색을 입힌 결과와 구분합니다. |
| 구간(span)·범위(range) | 원문에서 처리할 부분의 시작과 끝 위치입니다. `[start, end)`는 시작은 포함하고 끝은 제외합니다. 코드 색칠은 해당 구간에 색만 입힙니다. |
| 구문 트리(AST, Abstract Syntax Tree) | 파싱 결과를 제목·목록·문단 등의 계층으로 나타낸 자료입니다. 원문 문자열이나 화면의 뷰 계층과는 다릅니다. |
| 제외 구간(barrier) | 수식처럼 생긴 문자열이라도 수식으로 읽지 않는 부분입니다. 코드 블록 안의 수식 기호가 대표적인 예입니다. |
| 임시 덮기(mask) | 수식 구간을 임시 문자로 덮어 Markdown 분석에서 보호하는 처리입니다. Android는 UTF-16 길이를 유지하고 줄바꿈을 보존해 원문 위치가 어긋나지 않게 합니다. |
| 파싱 전 검사(preflight) | 구문 트리를 만들기 전에 입력 길이와 인용 깊이를 확인하는 처리입니다. 지나치게 큰 입력은 분석 전에 제한합니다. |
| 입력 제한을 적용한 값(bounded input) | 상한에 맞춰 처리한 문자열과 잘림 여부를 함께 보관한 값입니다. 모든 원문을 그대로 보관한다는 뜻은 아닙니다. |
| 입력 정규화(canonical·normalized input) | 같은 규칙으로 비교·처리하도록 입력을 정리하는 과정입니다. 이 문맥에서는 직접 만든 요청에도 입력 제한을 적용하고 기존 잘림 표시를 유지합니다. |
| 이스케이프(escape) | 문법 기호를 기능이 아닌 문자 그대로 읽도록 표시하는 처리입니다. 예를 들어 수식 구분 기호를 일반 글자로 표시할 때 필요합니다. |
| 코드 블록 구분 기호(fence) | 코드 블록의 시작과 끝을 표시하는 백틱 등의 기호입니다. 코드 본문 안의 `>`는 일반 코드 문자이므로 인용 깊이 검사에서 구분합니다. |

### UTF-8 바이트와 UTF-16 위치는 서로 다른 단위입니다

`A😀B`를 단순한 예로 들면 보이는 글자는 3개지만, UTF-16 코드 단위는 4개이고 UTF-8 바이트는 6개입니다. 이모지 하나가 UTF-16에서는 두 단위, UTF-8에서는 네 바이트를 차지하기 때문입니다. Kotlin `String.length`는 이 예에서 4이며, 이모지 범위는 `[1,3)`입니다. UTF-16의 두 코드 단위로 하나의 문자를 표현하는 조합을 **서로게이트 쌍(surrogate pair)**이라고 합니다.

Android Core의 원문 위치와 코드 색칠 범위는 **UTF-16 코드 단위**를 기준으로 합니다. 입력 상한은 **UTF-8 바이트**를 기준으로 합니다. iOS Core의 원문 위치는 UTF-8이므로 두 플랫폼의 위치 숫자를 그대로 교환하면 안 됩니다. 구현은 [Core 소스](../../richmarkdown-core/src/main/kotlin)의 `Utf16Range.kt`와 `InputLimits.kt`에서 확인할 수 있습니다.

**코드 포인트(code point)**는 유니코드 문자를 나타내는 값이고, **문자 묶음 경계(grapheme boundary)**는 결합 문자나 복합 이모지처럼 사용자가 한 글자로 보는 묶음의 경계입니다. 코드 포인트를 중간에서 끊지 않아도 복합 이모지 전체를 보존한다는 뜻은 아닙니다. 입력 제한과 Mermaid 실패 표시의 절단 규칙은 각각의 명세를 확인합니다.

## 비동기 요청과 최신 결과 표시

**코루틴(coroutine)**은 기다리는 동안 스레드를 계속 붙잡지 않고 나중에 실행을 이어갈 수 있는 작업입니다. `suspend` 함수라는 이유만으로 항상 별도 스레드에서 실행되는 것은 아닙니다. **디스패처(dispatcher)**는 코루틴을 어느 스레드에서 실행할지 정합니다. 표시 모델은 메인 스레드에서 요청·화면 반영을 관리하고, 계산을 `Dispatchers.Default`로 옮깁니다.

| 용어 | 뜻과 사용 예 |
| --- | --- |
| 요청 순서 번호(generation) | 어느 요청이 더 나중에 제출됐는지 구분하는 번호입니다. 이전 계산이 늦게 끝나도 현재 화면을 덮어쓰지 않도록 결과 반영 전에 비교합니다. |
| 같은 요청을 판별하는 기준(identity) | 원문·수식 인식 설정 등, 같은 계산을 재사용해도 되는지 확인하는 값입니다. 코드 색칠에서는 코드·언어·공급자 객체도 함께 비교합니다. |
| 캐시 키(cache key·content key) | 저장해 둔 계산 결과를 찾는 기준입니다. 수식 이미지에는 원문·색·크기 등이 필요하며 화면 요청의 순서 번호와는 용도가 다릅니다. |
| 최신 요청만 반영(latest-wins) | 여러 요청이 겹쳐도 가장 최근 요청의 결과만 현재 화면에 쓰는 규칙입니다. 이전 계산을 강제로 중단한다는 뜻은 아닙니다. |
| 대기 요청 합치기(coalescing) | 작업 하나를 실행하는 동안 대기 입력을 하나만 보관하고, 새 입력이 오면 그 대기 입력을 교체하는 방식입니다. |
| 최대 수신 번호(high-water) | 지금까지 받은 가장 큰 요청 순서 번호입니다. 더 최신 요청을 받은 뒤 늦게 도착한 이전 요청을 거절할 때 사용합니다. |
| 이전 요청의 결과(stale result) | 현재 입력이 바뀐 뒤 도착한 오래된 계산 결과입니다. 캐시에 저장할 수 있는지와 현재 화면에 표시할 수 있는지는 따로 판단합니다. |
| 결과 반영 조건(gate) | 계산 결과를 현재 화면에 써도 되는지 확인하는 조건입니다. 요청 번호·원문·설정이 현재 값과 맞는지 검사합니다. |
| 최신 상태 전달(StateFlow) | 가장 최근 상태를 보관하고 구독하는 쪽에 변경을 전달하는 Kotlin 도구입니다. 모든 중간 상태를 빠짐없이 보관하는 이벤트 목록은 아닙니다. |
| 작업 종료 상태(idle) | 실행 중이거나 대기 중인 작업이 없는 상태입니다. 취소나 실패 뒤에도 작업 실행기의 상태를 정리해야 다시 판단할 수 있습니다. |
| 수식 이미지를 나중에 채우기(hydration) | 문서를 먼저 표시하고, 아직 없는 수식 이미지가 계산되면 나중에 화면에 채워 넣는 과정입니다. |
| 실패 시 원문 표시(fallback) | 수식이나 다이어그램을 만들지 못했을 때 원문을 보여 주는 대체 처리입니다. 기능마다 표시 길이와 복사 데이터 보존 규칙은 다를 수 있습니다. |

단순화한 예로, A를 계산하는 동안 B가 대기하고 C가 들어오면 B 대신 C를 대기시킵니다. A 계산이 끝났다는 사실만으로 A를 화면에 표시하지는 않습니다. 화면에 반영하는 쪽에서 현재 요청과 맞는지 다시 확인합니다.

**잠금(lock)·직렬화(serialization)**는 공유 상태에 동시에 접근하지 않도록 순서를 정하는 방법입니다. 여기서 직렬화는 JSON으로 데이터를 바꾸는 뜻과 구분합니다. 작업 실행기는 대기 입력을 잠금 안에서 관리하지만 실제 계산은 잠금 밖에서 수행합니다.

**코루틴 취소**는 작업에 중단 요청을 전달합니다. 작업이 취소 상태를 확인하고 처리해야 하며, 이미 JavaScript 엔진 안에서 실행하는 계산까지 자동으로 강제 종료하지는 않습니다. `CoroutineStart.ATOMIC`은 시작 전 취소에도 정리 코드에 도달하도록 시작을 보장하는 데 사용하며, `ensureActive()`는 실제 입력을 처리하기 전에 취소 여부를 확인합니다.

## Compose·View와 수식 표시

| 용어 | 뜻과 사용 예 |
| --- | --- |
| 재구성(recomposition) | 상태가 바뀌면 Compose가 해당 화면을 다시 계산하는 과정입니다. 새 작업의 입력과 이전에 보관한 결과를 함께 확인해야 합니다. |
| `remember`·`LaunchedEffect` | `remember`는 Compose 상태를 보관하고, `LaunchedEffect`는 키에 맞춰 코루틴을 실행·취소합니다. 작업 키 변경만으로 이미 보관한 이전 결과가 새 입력의 결과로 바뀌지는 않습니다. |
| 화면 연결·분리(attach·detach) | View가 화면의 창에 붙거나 떨어지는 상태입니다. 다시 연결해 재사용할 수 있으므로 영구 폐기와 구분합니다. |
| 자원 해제·영구 폐기(release·dispose·destroy) | 더 쓰지 않을 엔진·뷰의 자원을 정리하는 처리입니다. API마다 재초기화 가능 여부가 다르므로 각 명세를 확인합니다. |
| 비트맵 이미지(raster·bitmap) | 점들의 색으로 구성한 이미지입니다. 공유 수식 이미지 경로에서 사용합니다. |
| 벡터 그림(vector·윤곽선 표현) | 선과 윤곽선 정보로 그리는 그림입니다. Compose와 View의 블록 수식은 이 표시 경로를 사용합니다. |
| 글자 기준선(baseline) | 글자들이 한 줄에서 맞춰지는 기준입니다. 인라인 수식이 주변 글자보다 뜨거나 가라앉지 않도록 맞출 때 사용합니다. |
| 수식 배치(layout·조판) | 수식 기호의 크기와 위치를 정하는 과정입니다. 수식 인식과 최종 그림 표시 사이의 단계입니다. |
| 프레임워크를 이용한 표시(native) | 이 문맥에서는 앱 쪽 Kotlin 코드와 Android의 텍스트·뷰 표시를 뜻합니다. 문서 전체를 웹 페이지로 바꾸는 방식과 구분합니다. |

Compose와 View는 같은 표시 모델 **클래스**를 사용하지만 각 화면에서 모델 객체를 따로 소유합니다. 모델의 최신 결과 검사와 각 뷰에 보관하는 수식·코드 색 상태의 검사는 별도로 확인합니다.

## Mermaid의 웹 표시와 보안

**WebView**는 앱 안에서 웹 문서를 표시하는 뷰입니다. **브리지(bridge)**는 앱 쪽 Kotlin 코드와 JavaScript가 원문·완료 결과·그림 크기를 주고받는 연결입니다. **WebViewAssetLoader**는 앱에 포함한 파일을 로컬 웹 주소로 읽게 하는 도구이며, 서비스 서버나 실행 중 번들 다운로드를 뜻하지 않습니다.

| 용어 | 뜻과 사용 예 |
| --- | --- |
| 웹 문서 구조(DOM) | 브라우저가 화면에 표시할 요소들을 보관하는 구조입니다. 최신 다이어그램 결과가 이 구조에 반영돼야 화면도 바뀝니다. |
| 요청 ID·페이지 로드 번호 | 요청 ID는 그림 계산·응답을 구분하고, 페이지 로드 번호는 다시 읽은 페이지를 구분합니다. 둘을 확인해 이전 응답이 현재 요청을 완료하지 못하게 합니다. |
| 완료 결과를 기다리는 객체(Promise) | JavaScript에서 나중에 성공하거나 실패할 작업의 결과를 나타내는 객체입니다. 끝나지 않는 Promise는 뒤 요청도 기다리게 할 수 있습니다. |
| 중단된 함수의 재개 수단(continuation) | 콜백이 끝났을 때 기다리던 코루틴을 다시 진행하게 합니다. 성공·실패·취소의 중복 응답을 그대로 반영하면 안 됩니다. |
| 표시 전 임시 영역(staging) | 그림을 화면에 내보내기 전에 크기와 현재 요청 여부를 확인하는 숨긴 영역입니다. 보이지 않는다는 이유만으로 스크립트 실행이 안전해지는 것은 아닙니다. |
| 화면 갱신 단계(frame) | 브라우저가 화면 배치를 갱신하는 단위입니다. 임시 영역에서 최종 크기를 확인한 뒤 실제 화면에 반영합니다. |
| 완료 대기 제한(deadline·timeout) | 일정 시간 안에 끝나지 않으면 오류로 처리하는 기준입니다. Mermaid의 로드와 렌더 대기는 각각 15초이며 전체 처리 시간이 15초 이내라는 보장은 아닙니다. |
| 다시 읽어야 하는 상태(dirty) | 취소·시간 초과 등으로 기존 페이지의 실행 상태를 이어 쓰기 어려운 상태입니다. 다음 요청 전에 페이지를 다시 로드합니다. |
| 원문 안의 설정(directive·frontmatter) | 다이어그램 원문에 포함한 렌더 설정입니다. 표시 설정과 안전 설정을 구분하고, 입력이 안전 설정을 임의로 바꾸지 못하게 합니다. |
| 콘텐츠 보안 정책(CSP) | 실행할 수 있는 스크립트와 불러올 수 있는 자원의 출처를 제한하는 브라우저 규칙입니다. 허용한 초기 코드의 해시와 로컬 번들만 실행하도록 설정합니다. |
| 위험한 태그·속성 제거(sanitizer) | HTML·SVG에서 위험한 태그나 속성을 걸러내는 처리입니다. 화면에 보이기 전에 실행된 스크립트까지 되돌려 주지는 않습니다. |
| 초기 실행 코드(bootstrap) | 페이지를 준비하고 Mermaid 실행 함수를 연결하는 시작 코드입니다. 이 코드가 바뀌면 CSP에 적은 해시도 맞춰야 합니다. |
| 묶음 파일(bundle)·포함 의존성 | Mermaid와 필요한 JavaScript 라이브러리를 묶어 앱에 넣은 파일입니다. Mermaid 본체 버전이 같아도 포함 라이브러리의 보안 수정으로 번들은 바뀔 수 있습니다. |

## 검사 결과를 읽는 방법

**회귀 테스트**는 수정 뒤 기존 기능이나 새로 고친 동작이 다시 깨지지 않는지 확인하는 검사입니다. **RED → GREEN**은 수정 전 테스트 실패를 확인하고 수정 뒤 통과를 확인했다는 표현입니다. 실행되지 않은 테스트는 실패를 재현한 근거로 삼지 않습니다.

**JVM·단위 테스트**는 해당 코드의 동작을 실행해서 확인하는 검사이며, **Android 계측 테스트(instrumentation test)**는 기기·에뮬레이터에서 Android API와 실제 엔진을 실행하는 검사입니다. **코드 실행 비율(coverage)**은 테스트가 소스의 어느 부분을 실행했는지 나타냅니다. 테스트 통과나 실행 비율만으로 모든 입력·기기·공격 상황을 확인했다고 해석하지 않습니다.

실제로 수행한 검사와 아직 확인하지 않은 범위는 [검수 기록](validation.md)에 구분합니다. 라이브러리 사용은 [문서 목차](README.md), 모듈 구조는 [전체 아키텍처](architecture/README.md)에서 이어 읽을 수 있습니다.
