# ADR-0001: JVM 코어의 2회 파싱과 최신 요청 합치기

상태: 소급 기록 — 현재 구현 확인 · 확인일: 2026-10-06

ADR(Architecture Decision Record)은 아키텍처 결정과 그 이유를 정리한 문서입니다. 여기서 소급 기록은 현재 구현을 읽고 선택을 나중에 설명했다는 뜻이며 당시 회의나 성능 비교를 복원한 기록은 아닙니다.

## 문제

수식 표기인 LaTeX의 `*`, `_`, `[`는 Markdown 원문을 분석하는 파서가 다른 의미로 읽을 수 있습니다. 반대로 수식을 먼저 찾으면 코드·링크 안의 원문을 수식으로 오인합니다. 스트리밍 입력마다 모든 요청을 끝까지 실행하면 대기 작업도 누적됩니다.

## 현재 선택

Android UI와 분리한 Java 가상 머신(JVM) 코어에서 첫 파싱으로 수식을 읽으면 안 되는 제외 구간과 문단 범위를 모읍니다. 원문 수식을 찾은 뒤 수식 구간을 임시 문자로 덮는 마스킹(mask)을 수행하고 두 번째로 파싱합니다. UI 렌더러는 그 결과인 공통 `ParsedDocument`만 읽습니다.

파싱 결과를 문단·링크·코드 같은 노드로 나타낸 문서 구조가 AST(추상 구문 트리)입니다. 두 번 만든 구조 사이에서 수식 구간을 보호하고 복원하는 것이 현재 방식의 핵심입니다.

원문 위치는 commonmark-java와 Kotlin `String`에 맞춰 UTF-16 단위로 기록합니다. UTF-16은 문자를 16비트 단위로 표현하는 방식으로 가상 예시 `A😀B`의 길이는 4이며 이모지가 두 단위를 차지합니다. 마스크도 같은 길이를 유지하므로 두 번째 파싱의 위치를 원문에 그대로 적용할 수 있습니다.

`CoalescingWorker`는 공유 상태를 동시에 바꾸지 못하게 하는 잠금(lock) 안에서 실행 여부·대기 입력·요청번호의 최대값을 관리합니다. 실행 중 1개는 유지하고 이후 요청은 최신 대기 입력(pending) 1개로 합칩니다. 단순화한 예로 A 실행 중 B·C가 도착하면 B 대신 C만 대기시키는 요청 합치기(coalescing) 방식입니다.

`generation`은 호출자가 붙이는 요청 순서번호입니다. 이전 결과를 화면에 반영하지 않도록 번호를 비교하는 검사(generation gate)는 호출자가 수행합니다. worker가 실행 중 요청을 취소하거나 그 결과를 자동 폐기하지는 않습니다.

![lock 안의 최신 pending 교체와 lock 밖의 단일 실행을 구분한 개념도](../assets/core-coalescing.svg)

그림은 잠금 안에서 최신 대기 입력을 교체하는 부분과 잠금 밖에서 실제 작업 하나를 실행하는 부분을 나눠 보여줍니다. 그림의 generation은 요청 순서이며 원문(source) 위치 단위와 무관합니다. iOS의 상태 보호 타입인 actor와 같은 목적을 갖지만 Kotlin 구현은 잠금과 하나의 처리 반복 작업(drain) 코루틴을 사용합니다.

## 비교한 대안과 비용

| 대안 | 얻는 점 | 현재 선택과 비교한 비용 |
| --- | --- | --- |
| 수식 정규식 전처리만 사용 | 파싱 횟수를 줄입니다. | 코드·HTML·링크 보호와 문단 전체 판정을 별도로 재구현해야 합니다. |
| CommonMark AST 노드 안에서만 수식 탐색 | 단일 AST 변환입니다. | 이미 분할된 수식을 원문 기준으로 복원하기 어렵습니다. |
| 모든 요청을 도착 순서대로 실행(FIFO) | 각 입력을 빠짐없이 처리합니다. | 스트리밍에서 이미 낡은 입력에 CPU와 대기 시간을 씁니다. |
| 요청마다 병렬 작업 생성 | 구현 입구가 짧습니다. | 동시 파싱·수식 작업과 결과 순서를 별도로 제한해야 합니다. |

2회 파싱은 CPU 비용이 있고 원문을 노드로 분석한 문서 구조(AST)를 유지해야 합니다. 가장 최근 입력을 남기는 latest-wins 방식은 중간 대기 입력을 버리므로 모든 입력 처리가 필요한 업무에 재사용하면 안 됩니다. `Int` generation은 계속 증가하는 번호를 전제로 하며 최대값 이후 값이 되돌아가는 wrap-around 처리는 없습니다.

두 `parse` 함수 형태(overload)는 입력을 제한합니다. 위치 조회용 내부 scanner는 입력을 자동 제한하지 않고 호출자가 제한한 원문을 요구합니다. 이 호출 조건은 scanner 입구에서 크기·깊이를 검사하는 iOS Core와 다릅니다.

2026-10-06 개선에서 시작 전 취소에도 상태 정리(cleanup)가 실행되도록 drain을 ATOMIC으로 시작합니다. ATOMIC은 취소됐더라도 코루틴 본문에 진입하게 하는 방식이며, 첫 취소 검사를 `try` 안에 두어 이미 취소된 작업 수명 범위(scope)의 실제 입력 실행은 막습니다. 예외 뒤 상태를 정리하고 살아 있는 scope는 다음 입력을 받을 수 있지만 취소된 scope 자체를 복구하지는 않습니다.

## 변경 판단과 근거

2회 파싱이 실제 병목으로 측정되면 파서 자체에 수식 문법 확장을 추가하는 방식(parser extension)과 비교합니다. 요청 이력 보존이 필요하면 최신 대기만 남기는 방식 대신 별도의 전달 계약을 선택합니다. 현재 구조의 명확성을 측정하지 않은 성능 수치로 평가하지 않습니다.

근거: [모듈 선언](../../../richmarkdown-core/build.gradle.kts), [소스](../../../richmarkdown-core/src/main/)의 `RichMarkdownParser.kt`, `MathProtector.kt`, `Utf16Range.kt`, `CoalescingWorker.kt`; [JVM 테스트](../../../richmarkdown-core/src/test/)의 파서·수식 보호 입력과 기대값(fixture), `CoalescingWorkerTest.kt`입니다. 이번 문서 작업에서 테스트를 새로 실행하지 않았으며 기존 실행 상태는 [검수 기록](../validation.md)을 참조합니다.
